- 기존 디자인과 바닐라 HTML/CSS/JS, Python Vercel 백엔드를 유지.

## 발견한 문제 → 변경 → 검증

1. 초대 코드 조회와 사용 처리가 분리되어 동시 가입 위험 → SQL 행 잠금과 단일 트랜잭션 도입 → 동일 코드 재사용 거부와 실패 시 회원 미생성 확인.
2. 소개 저장 API가 요청의 author_id를 신뢰 → Supabase Auth 토큰 검증 및 서버 UUID 사용 → 작성자 위조 입력과 미인증 호출 거부 확인.
3. 가상 데이터만 표시 → 실제 상태·초대·프로필·승인·매칭 API 및 DOM 연결 → 브라우저 테스트로 클릭부터 결과 표시까지 확인 (응답은 모의).
4. 주선자 수정 후 이전 승인이 남을 수 있음 → 승인 해제 및 읽은 버전 비교 → 오래된 화면의 승인 거부 확인.
5. AI 입력 검사만 구현 → Gemini Generate Content API 호출·실패 안내·초안 수정/전달 → 성공·한도·시간 초과·불완전 응답 테스트. 실제 AI 호출은 설정 대기.
6. 문서가 현재 코드보다 오래됨 → README·기획서·설정·데이터 설계·검증·증빙 상태 갱신.

## 스스로 설명할 학습 포인트

- HTML은 입력·버튼·섹션 구조, CSS는 반응형 배치와 스타일, JavaScript는 사용자 동작과 화면 갱신을 맡습니다.
- `js/session.js`가 입력을 JSON과 Bearer 토큰을 포함한 fetch 요청으로 보내고, Python이 인증 후 DB/AI를 호출하며, JavaScript가 JSON 결과를 textContent/textarea 값으로 표시합니다.
- Vercel은 Python 앱을 요청을 처리하는 함수로 실행합니다. 파일에 회원 정보를 저장하지 않고 Supabase에 보관하므로 함수 재실행 후에도 상태가 유지됩니다.
- 서버 키가 JavaScript에 들어가면 방문자가 읽을 수 있습니다. 서버 환경 변수만 사용하고 서버도 키를 응답에 포함하지 않습니다.
- 로컬 .env와 Vercel 환경 변수는 별개입니다. 로컬 성공 후에도 배포 변수·SQL 버전·진입점을 확인하고 수정·재배포해야 합니다.
- 모의 응답을 사용하는 테스트 성공과 실제 AI·배포 성공은 다릅니다. 최종 제출에는 실제 연결 검증이 필요합니다.
